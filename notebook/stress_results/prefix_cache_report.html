Prefix caching for the Retail Shopping Assistant: load test results

Nemotron 3.5 Super on vLLM, 4x NVIDIA H100 80GB · recorded shopper traffic replayed with AIPerf · September 28, 2026

Turning on prefix caching made the same hardware serve the assistant's real traffic faster and with more capacity. The benefit grows with load: at 64 concurrent conversations the server completed 46% more requests per second, and users waited 27% less for the first word of a reply, while each GPU drew less power.

What we tested

The workload

Real traffic from the assistant: 25 recorded shopper journeys, 897 model calls. Each call resends the system prompt, tool definitions and conversation so far, so prompts are long, averaging 11,058 tokens, while replies average 163 tokens. The replay sends every recorded prompt and forces each reply to its recorded length, so every run does the same work.

To load the server, each journey was copied with fresh identities: 50 conversations at 16 concurrent, 150 at 64.

What prefix caching does

Consecutive calls in a conversation start with the same text. With prefix caching, vLLM keeps the computed state for that shared beginning and reuses it, instead of recomputing the whole prompt every time. Nemotron 3.5 Super mixes attention and Mamba layers, so both kinds of state must be reused (--mamba-cache-mode align); otherwise the hit rate climbs but nothing gets faster.

We ran the same workload with caching on and off, at 16 and 64 concurrent conversations.

What it means

  • Caching pays off most under load. Its throughput gain grew from 21% at 16 conversations to 46% at 64. Without caching, GPU capacity goes to recomputing the same prompt beginnings; with it, that capacity serves more shoppers.
  • Replies also stream faster. Less recomputation leaves more room for generating replies: the median time between reply tokens fell 41% at 64 conversations (90 ms to 53 ms) and 16% at 16.
  • 16 conversations leaves the GPUs underused. On average only 11 of 16 requests were in flight, cache memory was 15% used, and quadrupling the load to 64 raised throughput 1.6x with caching on. The GPUs had headroom.
  • 64 without caching is saturated. The GPUs averaged 657 W against a 700 W limit, cache memory reached 100%, and requests queued. With caching on, the same load averaged 589 W and peaked at 88% cache memory.
  • The hit rate drops as load rises, from 62% at 16 to 55% at 64: more conversations compete for the same cache memory, so older entries are evicted sooner. The text of the trace suggests a ceiling of roughly 70 to 80%.
  • Choosing a load level is a trade-off. Going from 16 to 64 conversations with caching on gives 1.6x the throughput but roughly doubles time to first token (median 480 to 925 ms). The sweet spot lies between the two; 32 and 48 were not tested.
Recommendation: serve the assistant with prefix caching on, including Mamba state reuse (--enable-prefix-caching --mamba-cache-mode align). It costs nothing on this workload and improves every metric we measured.

Caveats

  • One run per setting. There are no repeats, so run-to-run variation is not measured. The differences at 64 conversations are large; the smallest ones, at 16, should be read as approximate.
  • About 0.2% of calls were flagged by AIPerf (26 of 14,352 calls total across the four runs): the model's reply had no text content, most likely because it was all reasoning or a tool call, which AIPerf does not count. The server reported no errors. These calls are excluded from the latency statistics, and the same calls recur in every run.
  • GPU power was recorded for the 64-conversation runs only. The recorder was added after the 16-conversation runs.
  • Time to first token includes a fixed floor of about 0.3 to 0.45 s per request, for request handling and tokenizing prompts of ~11,000 tokens, which caching cannot remove. Shorter prompts would lower it.
  • Model and software are pre-release: an early-access checkpoint on vLLM v0.30.0. Results may change with later releases.
  • Not tested: a single-conversation baseline, loads between 16 and 64, FP8 weights, or all 8 GPUs with expert parallelism.
